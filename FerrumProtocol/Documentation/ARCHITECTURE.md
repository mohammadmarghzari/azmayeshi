# Architecture

## Assemblies
- `FerrumProtocol.Runtime` — all gameplay code, ships in builds.
- `FerrumProtocol.Editor` — editor-only tooling (scene bootstrap, prefab generator).
- `FerrumProtocol.Tests.EditMode` — NUnit/Unity Test Framework tests for pure logic.

## Dependency Injection
No heavyweight DI framework is required for this scope. `Core/ServiceLocator.cs`
is a tiny static registry (`Register<T>`, `Resolve<T>`) that `GameManager`
populates on scene load. Systems depend on interfaces (`IEconomyService`,
`ISelectionService`, etc. — see `Core/Interfaces`), not concrete classes, so
they can be swapped/mocked in EditMode tests without booting a full scene.

## Data-Driven Design (ScriptableObjects)
Balance-relevant data (`UnitDataSO`, `BuildingDataSO`, `WeaponDataSO`,
`ArmorDataSO`, `FactionDataSO`, `ResourceTypeDataSO`, `TechTreeSO`) lives in
ScriptableObject assets, not hardcoded in MonoBehaviours. Designers (future
you) tune numbers without touching code or recompiling.

## Object Pooling
`Core/ObjectPool.cs` + `Core/ObjectPoolManager.cs` provide a generic pool keyed
by prefab reference. Projectiles, VFX, and short-lived UI elements should
always spawn through the pool manager, never `Instantiate/Destroy` directly,
once past the prototype stage.

## Networking (Mirror)
`Networking/RTSNetworkManager.cs` extends Mirror's `NetworkManager`. Design
rule: **the server is authoritative for all game state**. Clients send intent
(`Command` RPCs: "move these units here", "build this"), the server validates
and simulates, then replicates results (`SyncVar`/`ClientRpc`). This is the
same shape needed later for anti-cheat and replays — client input is never
trusted as fact.

## Fog of War
Grid-based visibility (`FogOfWar/FogOfWarManager.cs`): a low-resolution
byte grid tracks `Unseen / Explored / Visible` per cell, updated by
`FogRevealer` components (sight radius) on units/buildings. The grid is
uploaded to a `Texture2D` sampled by `Shaders/FogOfWarURP.shader` as a
world-aligned overlay. This scales far better than per-object raycasting.

## AI
`AI/AIController.cs` composes `EconomyAI`, `CombatAI`, and `BasePlanner`
behind an `AIDifficultyDataSO` that scales reaction time, aggression, and
economic efficiency — one difficulty asset per difficulty tier, no branching
`if (easy) ... else if (hard)` logic scattered through the codebase.

## Save System
`Save/SaveManager.cs` serializes `SaveData` DTOs to JSON on disk
(`Application.persistentDataPath`) by default. Cloud saves go behind
`ICloudSaveProvider` so a real backend (Steam Cloud, PlayFab, etc.) can be
dropped in later (Phase 5) without touching call sites.

## Why no scene/prefab files are hand-authored yet
Unity `.unity`/`.prefab` files are YAML with internal `fileID` cross-references
generated by the Editor's serializer. Hand-writing them outside Unity is
fragile and easy to corrupt. Instead, Phase 1 ships an **Editor automation
tool** (`Editor/SceneBootstrapper.cs` + `Editor/PrefabGenerator.cs`) that
builds the prototype scene and placeholder prefabs *from code, inside Unity*,
via `Menu: Ferrum Protocol > Build Prototype Scene`. This is safer and is
also just a genuinely useful, reusable tool going forward.
